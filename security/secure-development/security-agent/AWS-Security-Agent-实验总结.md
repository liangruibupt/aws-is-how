# AWS Security Agent 实验总结

## 一、Security Agent 是什么

AWS Security Agent 是一个 AI 驱动的安全工具，集成在 Kiro IDE 中。它可以自动扫描代码漏洞、对需求和设计文档进行威胁建模、对运行中的应用执行渗透测试，并在 CI/CD 流水线中充当安全门禁。

核心定位：**把安全检查嵌入开发全流程，而不是等到上线后再补救。**

### 核心能力

| 能力 | 说明 | 触发时机 |
|------|------|----------|
| **威胁建模（Threat Model Review）** | 基于需求文档和设计文档分析安全态势，使用 STRIDE 框架识别威胁 | 需求与设计阶段 |
| **代码安全扫描（Full Scan）** | 对整个代码库做全量静态分析，识别 SQL 注入、命令注入、路径穿越等漏洞 | 手动触发，或合并到主分支后由 CI 执行 |
| **差异扫描（Diff Scan）** | 只扫描 git diff 变更的代码（以完整仓库为上下文），速度更快 | 提交前、创建 MR 前 |
| **MR 代码评审（Code Review）** | 自动对 GitLab MR 的变更代码发表评审意见 | 创建或更新 MR 时自动触发 |
| **CI 安全门禁（Review Gate）** | 在 CI 流水线中阻断含安全问题的合并请求 | MR 流水线自动执行 |
| **渗透测试（Penetration Test）** | 对运行中的应用发起真实攻击请求，验证漏洞是否可被实际利用 | 部署到测试环境后 |

## 二、架构：各组件如何协作

Security Agent 的工作涉及三个层面：Kiro IDE（本地）、AWS 云端服务、GitLab 代码托管。

### 2.1 Kiro IDE 与 AWS 云端

```
┌──────────────────────────────────────────────────────────┐
│                     Kiro IDE（本地）                       │
│                                                          │
│  ┌─────────┐    MCP 协议     ┌─────────────────────┐     │
│  │  Kiro   │ ◄────────────► │  Security Agent     │     │
│  │  AI     │   工具调用/结果  │  MCP Server         │     │
│  │  Agent  │                │  （本地子进程）        │     │
│  └─────────┘                └──────────┬──────────┘     │
│                                        │                 │
└────────────────────────────────────────│─────────────────┘
                                         │
                          打包代码上传 S3  │  调用 AWS API
                          轮询状态/结果    │
                                         ▼
                    ┌──────────────────────────────────┐
                    │        AWS 云端                    │
                    │                                    │
                    │  ┌────────┐    ┌───────────────┐  │
                    │  │   S3   │    │ Security Agent│  │
                    │  │ Bucket │───►│   Service     │  │
                    │  └────────┘    │               │  │
                    │                │  · 代码扫描    │  │
                    │                │  · 威胁建模    │  │
                    │                │  · 渗透测试    │  │
                    │                └───────┬───────┘  │
                    │                        │          │
                    │                ┌───────▼───────┐  │
                    │                │  Agent Space  │  │
                    │                │  （扫描空间）   │  │
                    │                └───────────────┘  │
                    └──────────────────────────────────┘
```

| 组件 | 位置 | 职责 |
|------|------|------|
| **Kiro AI Agent** | 本地 IDE | 接收用户指令，调用 MCP 工具，展示结果，执行修复 |
| **Security Agent MCP Server** | 本地子进程 | Kiro 和 AWS 云端之间的桥梁。负责打包代码、上传 S3、调用 AWS API、轮询状态、获取结果 |
| **S3 Bucket** | AWS 云端 | 存储上传的代码压缩包和 diff 补丁文件 |
| **Security Agent Service** | AWS 云端 | 执行实际的安全分析（代码扫描、威胁建模、渗透测试），生成 Finding |
| **Agent Space** | AWS 云端 | 扫描的工作空间，关联 S3 存储桶和 IAM 角色，隔离不同项目的扫描资源 |

**核心设计理念**：

- **计算在云端，交互在本地**。MCP Server 只是"快递员"——把代码打包送上云端，把分析结果取回来。真正的漏洞检测、威胁建模、渗透测试全部由 AWS 云端完成。
- **MCP 协议解耦**。Kiro Agent 不直接调用 AWS API，而是通过 MCP 标准协议与 MCP Server 交互，不需要关心 S3 上传、API 签名等底层细节。

### 2.2 与 GitLab 的集成

Security Agent 与 GitLab 通过 **两个独立通道** 协作：

```
                    ┌──────────────────┐
                    │     GitLab       │
                    │   (EC2 自建)     │
                    │                  │
                    │  · 代码仓库       │
                    │  · MR 管理       │
                    │  · CI 流水线      │
                    │  · Comment 评审   │
                    └──┬──────────┬────┘
                       │          │
          ┌────────────┘          └────────────┐
          │ 通道 A：MR 代码评审                   │ 通道 B：CI 流水线
          │ （自动触发）                          │ （Job 执行）
          ▼                                     ▼
┌───────────────────────┐        ┌──────────────────────────┐
│  Security Agent       │        │  CI Runner               │
│  Code Review Bot      │        │                          │
│                       │        │  security-agent-review   │
│  · 监听 MR 创建/更新   │        │  -gate.sh：              │
│  · 自动分析变更代码     │        │  · 轮询 MR Comment       │
│  · 在 MR 中发表 Comment │        │  · 等待 Agent 评审完成    │
│  · "No issues" 或列出  │        │  · 无问题 → 门禁通过      │
│     具体 Finding       │        │  · 有 Finding → 阻断     │
└───────────────────────┘        └──────────────────────────┘
```

**通道 A — MR 代码评审（自动）**

Security Agent 以 GitLab 用户 `@aws-security-agent` 的身份接入仓库。开发者创建或更新 MR 时，Agent 自动分析变更代码，在 MR 的 Activity 区域发表 Comment：先提示"正在评审"，几分钟后给出结果——无问题则 "No issues identified"，有问题则逐一列出 Finding。

**通道 B — CI 安全门禁（流水线 Job）**

CI 流水线中的 `security-agent-review-gate` Job 不直接调用 Security Agent API，而是通过 **轮询 GitLab MR 的 Comment** 来判断结果。看到 "no issues identified" 则门禁通过；看到含 "severity" 的 Finding 则阻断流水线，要求人工审批后才能合并。

**巧妙之处**：CI 门禁只需要 GitLab Token 来读取 MR Comment，不需要 AWS 凭证。评审结果和门禁判定通过 GitLab Comment 这个"公告板"解耦。

## 三、安全贯穿全流程：从需求到上线

Security Agent 不是某个阶段的工具，而是贯穿软件开发全生命周期的安全伙伴。

### 阶段一：需求与设计 — 威胁建模 + 规则审核

```
产品需求文档
    │
    ▼
编写 requirements.md / design.md
    │
    ▼
Security Agent 威胁建模（Threat Model Review）
    │
    ├── 输入：需求文档 / 设计文档 + 项目源码
    ├── 分析：基于 STRIDE 框架识别设计层面的安全威胁
    ├── 输出：威胁列表（严重性、STRIDE 分类、影响、修复建议）
    │
    ▼
对照安全基线（security-baseline.md）逐条审核
    │
    ├── 是否有硬编码密钥？
    ├── 输入是否做了校验和白名单约束？
    ├── 是否存在与安全规则的冲突？需要记录例外和理由
    │
    ▼
修改设计 → 消除威胁 → 进入开发
```

**Security Agent 对需求文档的安全审核**

Security Agent 的威胁建模（`start_threat_model_review`）不只是分析代码，它可以直接接收需求文档（`requirements.md`）和设计文档（`design.md`）作为输入：

- **需求阶段就能介入**：不需要等代码写完。只要有 requirements.md，Agent 就可以审核需求本身是否引入了安全风险。比如需求中要求"匿名访问"，Agent 会标记这与认证授权规则的冲突。
- **设计文档作为 scope**：传入的 spec 文件会被 Agent 作为优先分析范围（scope documents），分析更聚焦、结果更有针对性。
- **输出可操作的威胁清单**：每个威胁包含 STRIDE 分类、严重性、影响描述、受影响资产和修复建议，可以直接指导设计文档的修改。
- **与 Kiro Spec 工作流集成**：编写完 requirements.md 和 design.md 后、生成 tasks.md 之前，是做威胁建模审核的最佳时机——在实现开始之前就把安全问题拦截在设计层。

**什么是 STRIDE**

STRIDE 是微软提出的经典威胁建模框架，从六个角度系统性地审视安全风险：

| 字母 | 英文 | 含义 | 典型问题 |
|------|------|------|----------|
| **S** | Spoofing | 伪造身份 | 攻击者能冒充合法用户吗？ |
| **T** | Tampering | 篡改数据 | 请求或响应能被篡改吗？ |
| **R** | Repudiation | 抵赖 | 操作能被追溯和审计吗？ |
| **I** | Information Disclosure | 信息泄露 | 能看到不该看的数据吗？ |
| **D** | Denial of Service | 拒绝服务 | 能让服务瘫痪吗？ |
| **E** | Elevation of Privilege | 提权 | 能获取超出预期的权限吗？ |

做威胁建模时，对系统中的每个组件和数据流逐一用这六个角度提问，就能系统性地覆盖主要威胁类型，避免遗漏。

**这个阶段能发现什么**：架构层面的缺陷，比如"匿名接口可以下载数据库"、"缺少权限校验"。这些问题如果到代码写完才发现，返工成本远高于设计阶段修改文档。

### 阶段二：开发 — 代码扫描 + MR 评审 + CI 门禁

```
开发者在 Kiro IDE 中编写代码
    │
    ├── Steering 文件自动加载安全基线，实时约束编码行为
    │
    ▼
代码写完，提交前做差异扫描（Diff Scan）
    │
    ├── 只扫描变更的代码，几分钟出结果
    ├── 发现问题 → 当场修复 → 再扫一次验证
    │
    ▼
推送代码，创建 MR
    │
    ├── Security Agent 自动评审 MR 代码变更
    │   ├── 发表 Comment："正在评审..."
    │   └── 发表 Comment：列出 Finding 或 "No issues identified"
    │
    ├── CI 安全门禁轮询评审结果
    │   ├── 无问题 → 门禁通过 ✅
    │   └── 有 Finding → 阻断合并 ❌ → 修复后重试
    │
    ▼
合并到主分支 → 全量代码扫描（Full Scan）
    │
    └── 全面审计，作为安全基线的定期检查
```

**这个阶段能发现什么**：代码实现层面的漏洞，比如 SQL 注入、路径穿越、日志注入。自动化门禁确保有问题的代码无法合并。

### 阶段三：部署后 — 渗透测试

```
应用部署到测试/生产环境
    │
    ▼
Security Agent 渗透测试（Penetration Test）
    │
    ├── 注册目标域名并验证所有权
    ├── 对运行中的应用发起真实 HTTP 攻击请求
    ├── 尝试各种攻击向量：
    │   ├── IDOR — 越权访问其他用户的数据
    │   ├── 注入 — SQL、命令、路径穿越
    │   ├── 认证绕过 — 未授权访问受保护接口
    │   ├── 信息泄露 — 错误信息、调试接口暴露
    │   └── 其他 OWASP Top 10 攻击
    │
    ▼
生成渗透测试报告
    │
    ├── 确认哪些漏洞可以被实际利用
    ├── 提供攻击证据（请求/响应日志）
    │
    ▼
修复 → 重新部署 → 再次渗透测试验证
```

**这个阶段能发现什么**：运行时才暴露的业务逻辑漏洞。比如 IDOR（代码语法完全正确，参数化查询也没问题，但业务逻辑缺少权限判断）——这类问题静态扫描很难发现，只有真实请求才能暴露。

### 全流程总览

```
需求 ──────► 设计 ──────► 开发 ──────► 提交 ──────► 部署 ──────► 运行
  │            │            │            │            │            │
  │         威胁建模      代码扫描     MR 评审      全量扫描     渗透测试
  │         规则审核     （Diff Scan） CI 门禁    （Full Scan）
  │            │            │            │            │            │
  ▼            ▼            ▼            ▼            ▼            ▼
发现设计      发现架构     发现代码      阻断有       全面审计     验证真实
层面风险      层面威胁     层面漏洞      漏洞的MR     代码库       可利用性
  │            │            │            │            │            │
  └────────────┴────────────┴────────────┴────────────┴────────────┘
                              │
                    越早发现，修复成本越低
```

## 四、Kiro IDE 中的工具参考

在 Kiro 中通过 MCP 协议调用 Security Agent，主要工具：

| 工具 | 用途 |
|------|------|
| `setup_check` | 检查 AWS 凭证、Agent Space 是否就绪 |
| `setup` | 首次使用时创建 Agent Space 和 IAM 角色 |
| `start_threat_model_review` | 启动威胁建模（接收需求/设计文档 + 源码） |
| `start_security_scan` | 启动全量代码扫描 |
| `start_diff_scan` | 启动差异扫描（只扫变更部分） |
| `get_scan_status` | 查询扫描进度 |
| `get_scan_findings` | 获取扫描发现（支持扫描进行中查看部分结果） |
| `list_scans` | 列出历史扫描记录 |
| `stop_scan` | 取消正在运行的扫描 |

典型调用流程：

```
setup_check → 确认环境就绪
    ↓
start_security_scan / start_diff_scan / start_threat_model_review → 启动（立即返回 scan_id）
    ↓
get_scan_status → 轮询等待完成（全量约 30-45 分钟，差异约 10-15 分钟）
    ↓
get_scan_findings → 获取结果，按严重性分级展示
    ↓
修复 → 再次 diff scan 验证
```

## 五、关键收获

1. **安全左移**：通过 Steering 文件将安全基线嵌入 IDE，在写代码的时候就自动检查。通过威胁建模在需求和设计阶段就拦截架构层面的安全缺陷，而不是等到代码评审或上线后才发现问题。

2. **需求阶段就能做安全审核**：Security Agent 可以直接分析 requirements.md 和 design.md，不需要等代码写完。越早发现问题，修复成本越低。

3. **自动化门禁是安全的最后防线**：CI 流水线中的 Security Agent 门禁确保即使开发者遗漏了安全问题，含有漏洞的代码也无法合并到主分支。

4. **渗透测试验证真实风险**：IDOR 漏洞在代码静态分析中不一定能被发现（查询本身是参数化的，语法没有问题），但渗透测试通过真实请求暴露了业务逻辑层面的权限缺失。

5. **分层防御，缺一不可**：没有单一手段能覆盖所有安全风险。威胁建模发现设计缺陷、代码扫描发现实现漏洞、渗透测试验证可利用性——层层递进才能构建完整的安全体系。
