执行摘要 Executive Summary

  1. 国际主流电商/支付已全面拥抱标准 Passkey（FIDO2/WebAuthn）。PayPal（2022 起）、Amazon、eBay、Best Buy、Target、Shopify（Shop Pay）均已上线，抗钓鱼、免密、跨设备是共同价值主张。
  2. 真正的瓶颈从"注册"转向"使用率"。PayPal 公布的漏斗显示：eligible→enroll→login 逐级衰减，端到端实际使用约 8%——"utilization, not enrollment, is the next problem"。
  3. 中国走的是另一条路：IFAA/IIFAA + TEE/SE 本地生物识别授权 + 服务端风控 + 实名绑定，而非标准 WebAuthn。技术上是"match-on-device 解锁设备密钥"，但凭证体系、监管（实名/支付合规）与国际 passkey 不同源。出海时需要两套心智。
  4. 技术落地的三大生死线：rp.id 用可注册域（eTLD+1）、账户恢复不能弱于 passkey、signCount 不能再用于克隆检测（synced passkey 恒为 0）。
  5. AWS 落地：Amazon Cognito 已原生支持 passkey（WebAuthn）作为托管 RP；自建 RP 则用 API Gateway + Lambda + DynamoDB（凭证存储）+ KMS，配 WAF/Fraud Detector 做风控，形成"抗钓鱼登录 + 服务端风控"的完整闭环。

全球格局：两条技术路线 Standard WebAuthn vs. IFAA/TEE 本地授权

路线 A — 国际标准 Passkey

FIDO2 = WebAuthn(浏览器/RP API) + CTAP2(平台/漫游认证器)。用户设备生成非对称密钥对，私钥留在设备/云同步（iCloud Keychain、Google Password Manager、1Password），公钥交给 RP。登录时本地生物识别/PIN 解锁私钥，对 RP 挑战签名。抗钓鱼来自密钥与 origin(rp.id) 强绑定。

凭证=公私钥对origin 绑定跨厂商可移植

路线 B — 中国 IFAA/IIFAA + TEE

IFAA（互联网金融身份认证联盟，2015-06 蚂蚁牵头，后演进为 IIFAA）：生物特征模板与匹配全在设备 TEE/SE 内完成（match-on-device，模板不出端），本地授权后解锁设备侧密钥；再叠加强制服务端风控与实名绑定。是"金融级可互操作认证"，但不是标准 WebAuthn 凭证体系。

match-on-deviceTEE/SE+ 服务端风控 + 实名
为什么中国走了不同的路？ 时间上 IFAA(2015) 早于 FIDO2/WebAuthn 大规模落地；监管上支付需实名与强风控，"纯凭证抗钓鱼"不足以满足合规；生态上 iOS/Android + 国产 ROM 的 TEE 能力被支付宝/微信直接调用，形成事实标准。近年 IIFAA 也在向 FIDO/passkey 靠拢（互操作性演进），但存量仍以本地生物识别授权为主。
来源：ITU/IFAA 演讲材料、IFAA 指纹支付专利 CN107133794、阿里云 IDaaS(IFAA SDK) 文档。

跨平台的产品共识

  • 不强制、可并存：passkey 与密码/OTP 长期共存，opt-in 引导，绝不断掉旧路径。
  • 时机要对：成功登录后、结账后、或安全提醒后引导，转化最高；冷启动强弹易被忽略。
  • 价值话术具体化："更快""不用记密码""更安全"，而非讲 WebAuthn 术语。
  • 移动优先：平台认证器（Face ID/指纹）+ App 内注册是主战场。

对出海/国际化电商的启示：
  • 面向海外市场直接上标准 FIDO2/WebAuthn passkey——这是 Apple/Google/微软生态的默认能力，兼容成本最低。
  • 面向中国市场则复用支付宝/微信的本地生物识别 + 免密协议，并满足实名与支付合规，不能简单套用 WebAuthn。
  • 两套心智：国际是"抗钓鱼凭证"，中国是"本地授权 + 服务端风控 + 实名"。服务端风控（设备指纹、行为、限额、异常升级）在两条路线里都不可省。

产品 / UX 最佳实践 注册引导 · 登录体验 · 跨设备 · 降级

注册引导（Enrollment）

  • 时机：成功登录后 / 结账后 / 安全提醒后，弹一次性引导；可跳过、不阻断。
  • 渐进式：先在移动 App（平台认证器）落地，再扩到 Web。
  • 入口常驻：账户安全设置里能随时添加/命名/删除 passkey（用 AAGUID 显示 provider 名）。
  • excludeCredentials：注册时排除已有凭证，避免同设备重复注册。

登录体验（Sign-in）

  • Conditional UI（autofill）：mediation:"conditional" + autocomplete="username webauthn"，让 passkey 出现在账号自动填充里——先做 feature-detect。
  • 默认优先：每次登录默认呈现 passkey，而非藏进"更多方式"。
  • 多 passkey 管理：允许多设备/多 provider 各存一个。

跨设备（Cross-device / Hybrid）

  • CTAP2 hybrid：手机扫 Web 端二维码，蓝牙做邻近性校验防远程中继；凭证仍绑 origin。
  • 用于"新电脑上用手机 passkey 登录"这种典型场景。

企业 / 共享设备

  • 共享/公用机器不建本地平台 passkey，改用 hybrid（个人手机作认证器）。
  • 高权限账户用 device-bound 硬件 key（AAL3）。

Synced vs Device-bound Passkey

Synced（iCloud / Google / 1Password）

可用性与恢复最好（换机自动带过去），但安全边界集中到 provider 云账户；signCount 恒为 0；无法做设备克隆检测。适合普通消费者（AAL2）。

Device-bound（硬件 key / 平台绑定）

保证最高（AAL3），私钥不离设备；丢设备即丢凭证，需备用 key。适合管理员 / 高权限账户。

attestation 用不用？消费级识别 provider 只需 AAGUID（16 字节型号标识，仅注册时出现，assertion 里没有——注册时必须抓取存下），不必开 attestation；只有需要证明"确实是某型号合规硬件"时才用 direct attestation。

账户恢复：最容易被忽视的最弱环节 Account Recovery

核心命题：系统的实际安全 = 恢复路径中最弱的一环。主凭证是抗钓鱼 passkey，但恢复却靠 email / SMS OTP，攻击者会直接打恢复通道接管账户——passkey 的抗钓鱼优势被绕过。

推荐设计

  • 多 passkey 优先：鼓励用户注册多个（多设备 + 多 provider），把"恢复"变成"再用另一个 passkey 登录"。
  • 受控 OTP 兜底：保留 email/OTP 但加限速、异地/异常延时、二次确认。
  • 高价值操作多因素/延时：改密、绑卡、大额支付触发 step-up + 通知窗口。
  • synced 的隐性依赖：要意识到 synced passkey 的恢复其实依赖 iCloud/Google 账户安全——那才是真正的信任根。

常见坑 / 反模式 Anti-patterns

❌ 1. 用 signCount 做克隆检测

synced passkey 计数恒为 0，"signCount is dead"。存但别据此拒登。

❌ 2. rp.id 设成完整主机名

www.shop.com 而非 shop.com → 子域间失效。

❌ 3. 忘存 AAGUID / transports

AAGUID 仅注册可得，事后无法补；影响管理 UI 与 UX 优化。

❌ 4. 恢复通道弱于 passkey

OTP 恢复直接抵消抗钓鱼价值。

❌ 5. 消费级强开 direct attestation

增加摩擦与隐私顾虑，多数场景无必要。

❌ 6. 不做 conditional-UI feature-detect

老 OS/webview 不支持时体验崩坏。

❌ 7. 缺 excludeCredentials

同设备重复注册，管理混乱。

❌ 8. 把 passkey 藏进设置页

注册后不在登录时优先呈现 → 使用率停在个位数。

Passkey 方案在 AWS 上的服务映射 托管 RP vs 自建 RP

WebAuthn 里 RP（Relying Party，依赖方）就是电商后端。在 AWS 上落地有两条路：用 Amazon Cognito 作为托管 RP（最快），或自建 RP（最大控制力）。下面把 passkey 方案的每个职责映射到具体 AWS 服务。

关键设计点

  • rp.id = 站点 eTLD+1，与 CloudFront 域一致。
  • challenge 存 DynamoDB（TTL 短，如 120s），verify 时校验并删除（防重放）。
  • 凭证表 GSI on credential_id（登录时按凭证反查用户）。
  • 验签用成熟库（SimpleWebAuthn / py_webauthn），别手写 CBOR/COSE 解析。

风控闭环（对齐"服务端风控"路线）

  • WAF：登录端点限速 + AWS Managed Bot Control。
  • Fraud Detector：设备/行为/地理特征打分，高风险触发 step-up。
  • 敏感操作（改密、绑卡、大额）强制 userVerification=required + 通知窗口。
  • CloudWatch 指标：passkey 登录成功率、时延、回退率、ATO 事件。

混合建议（生产推荐）

大多数电商可以 Cognito 做身份与 passkey RP（省掉 WebAuthn 验签的自研与合规负担），再叠加 WAF + Fraud Detector 做服务端风控、用 Lambda + DynamoDB 承接业务侧的设备指纹/限额/审计扩展。只有当你需要精细控制 WebAuthn 协议参数或已有自建 IdP 时，才走全自建 RP。
